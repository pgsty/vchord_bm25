# vchord_bm25 相对 bc817b3 的性能与正确性验收

2026-11-24。基线为 1.2.0 标签对应的 `bc817b3`，受测代码为本地分支 `codex/bm25-performance` 的 `2755c6d`。构建、维护和查询两表中的箭头表示同机的基线 → 修改版。

两个分类各有 2,000 行。分类 2 的高分行靠前，BM25 可以较早停止。分类 1 取 100 行时需要多轮扩批，约 11.1 万次块访问，相对基线在两台各慢约 20%。修改版对同一 SQL 禁用 BM25 扫描后，Bitmap + Sort 的本机和 m3 延迟分别为 9.26 ms、12.33 ms。规划器能估计过滤比例，但现有统计量不能告诉它合格行在 BM25 名次中的分布。此次定价考虑第一次准备、首批 WAND 和后续扩批，保留真实选择率，规划阶段只读已有关系元数据。

20,000 行标量评分复用执行期间验证过的索引身份和 seed，少了 19,999 次共享块访问。单行评分仍需读取 growing，才能得到精确的文档数、词的文档频率和平均文档长度。已完成的非 NULL 物理记录按现有口径计数，包含压实前的墓碑。在 10,000 行 sealed 数据上追加 100 行含新热词的文档。两台机器上的两个版本都选中旧稀有词，索引与标量评分一致。

使用 40 个 growing 页、2,000 条构造记录的 Rust 探针测得下列缓存保留字节。计量使用 `Prepared::approximate_size()`，进程峰值内存另在并行构建测试中采样。

| growing 命中数 | 基线标量 / 扫描 | 修改版标量 | 修改版扫描 |
| --- | --- | --- | --- |
| 0 | 69,896 | 4,424 | 5,960 |
| 20 | 69,896 | 4,424 | 6,728 |
| 2,000 | 69,896 | 4,424 | 55,112 |

扫描保留正分候选和每页完成记录的位置。进入零分或 NULL 尾部时，沿固定截点从相应页续读。上述稀有词 Top‑10 因此由 994 增至 1,030 次块访问，两台均有小幅延迟回退。标量与扫描共用同一代和截点，翻页期间的追加、墓碑与备库回放均有验证。

## 原型取舍

**#4 合入同链最多三页的原子回收。** 一条 Generic WAL 同时推进 jump 并标记退役页，提交后才在页锁内向 FSM 报告。使用 #4 前后的构建，每台、每版本各做四次交叉试验，每次四个客户端持续插入并执行十轮实际回收的 VACUUM。先计算各次试验与 VACUUM 重叠的 INSERT 延迟分位数，再取四次中位数。

| 平台 | INSERT p95（ms） | INSERT p99（ms） | VACUUM（ms） | 重叠窗口内 INSERT 数 |
| --- | --- | --- | --- | --- |
| 本机 | 0.209 → 0.212 | 0.280 → 0.297 | 18.59 → 13.24 | 23,787 → 17,779 |
| m3 | 0.162 → 0.166 | 0.243 → 0.262 | 15.63 → 11.66 | 31,709 → 22,910 |

两台典型 p99 都有小幅上升，约 16–19 微秒。首次与其他负载重叠的本机试验还观察到 1.66 → 2.24 ms。决定合入的依据是回收 WAL 条数下降约三分之二、字节下降约 47%，同时每轮 VACUUM 的持续时间缩短。四客户端是本次验证过的并发度。

**#10 合入可重复求值的相关子计划预过滤。** 对同一条相关 `count(*)` SQL 依次关闭、开启、开启、关闭预过滤。四次均使用 `Limit → BM25 Index Scan → Aggregate → B-tree Index Only Scan`，十行结果及顺序相同。

| 平台 | 关闭 → 开启，块访问 | 关闭 → 开启，ms |
| --- | --- | --- |
| 本机 | 166,279 → 30,220 | 14.49 → 4.25 |
| m3 | 166,271 → 30,219 | 19.40 → 6.68 |

支持范围包括已确认可重复求值的普通堆扫描、B-tree 扫描、Result 和简单的内建 `count(*)` 聚合。易失表达式、未知节点及安全敏感过滤由执行器处理。LATERAL 重扫和易失函数调用次数均有回归覆盖。

**#6 保留 PostgreSQL 的默认并行度选择。** 100,000 行中英长文档，主堆 47.6 MiB，TOAST 表及其索引 329.4 MiB，`maintenance_work_mem=64MB`。各档测量两次，并从日志核实实际启动数。RSS 是参与进程合计峰值，共享页可能重复计入。m3 另采样了私有页。

| 实际 worker 数 | 本机 s | m3 s | 本机 RSS MiB | m3 RSS MiB | m3 私有 MiB | 临时文件峰值 MiB（本机 / m3） |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 2.47 | 2.49 | 378 | 459 | 257 | 847 / 803 |
| 1 | 1.59 | 1.65 | 701 | 790 | 239 | 781 / 780 |
| 2 | 1.37 | 1.33 | 963 | 1,013 | 286 | 764 / 753 |
| 4 | 1.21 | 1.09 | 1,328 | 1,393 | 401 | 680 / 588 |
| 默认 → 1 | 1.61 | 1.67 | 698 | 770 | 216 | 789 / 689 |

增加 worker 主要缩短扫描阶段，写出索引仍需时间。这个 TOAST 负载从 4 个 worker 获益，也消耗了更多内存。保留表级 `parallel_workers`，允许业务按机器和并发维护预算选择。

**#1b 及其余构建检查点改动暂缓。** 以下原型均以已含 #1 的版本为对照。本机每个原型建索引三次，对照在首尾共六次。

| 本机独立构建原型 | Generic WAL 条数 | WAL 字节 | 耗时 ms |
| --- | --- | --- | --- |
| 仅 #1 | 3,861 | 15,126,544 | 424.8 |
| 仅文档输出带检查点 | 3,840 | 15,125,680 | 415.6 |
| 仅地址树空页检查点 | 3,858 | 15,126,728 | 408.1 |
| 仅私有输出带与成对写页 | 3,861 | 15,081,056 | 406.9 |
| 地址树与私有输出带合并原型 | 3,858 | 15,080,744 | 411.4 |

地址树与私有输出带合并原型只节省约 0.3% 的 WAL 字节。在另一轮测量中，它耗时 514.5 ms，对照为 504.8 ms。文档输出带独立修改约省 20 条 WAL，地址树约省 3 条。在当前样本上，这些收益不足以增加不同的页链接和中断处理路径。

## 授权与其余决定

- **#2** 的 `shared_corpus_stats` 为索引所有者控制的存储参数，默认 off。显式开启后，已有语料读取权限的角色可使用全索引统计，评分可以反映跨租户的词分布。标量、扫描和视图共用语料权限检查，RLS 表的行策略与查询过滤由执行器处理。验证覆盖普通角色、FORCE RLS、BYPASSRLS、`row_security=off`、撤销授权、仅有视图授权，以及表达式和部分索引的列权限与函数执行权限。
- **#14** 的构建进度由每个参与者每 1,024 行报告一次，同步前补齐余数。实际行数与 broken HOT chain 独立汇总。**#5** 保留严格索引身份验证，在文档中给出固定索引并参数化检索词的通用计划写法，可用于 RRF 的 BM25 分支。
- **#9** 保留 `PARALLEL RESTRICTED`，跨 worker 共享同一物理统计截点仍需独立实现。**#13** 保留 pgrx 拥有型 RHS，已验证的收益来自执行期元数据复用。**#11** 的既有插桩样本在 12 批中只调用一次 `positive_documents()`。**#12** 的多词求和与插入退避、**#15** 的普通 SQL 执行器钩子均缺少足以支持改动热路径的实测收益。

## 验收与复核

- 本机 macOS arm64 PG 18.7、m3 Ubuntu x86_64 PG 18.6 分别通过 19 个 SQLLogicTest 文件、独立评分公式、WAND 舍入与完整翻页、HOT、并发 VACUUM 和 `acceptance.py --slt --recovery`。并发读者的旧快照返回 5,100 个不同 ID，新快照返回 10,100 个。
- 两台都通过构建和退役中途取消、崩溃重启、丢失 FSM 后修复，以及物理备库 `40001` 和墓碑回放。测试备库使用专用物理复制槽保留所需 WAL。确定性单元测试检查多条回收 WAL 的每个回放前缀。
- 两台都用真实 1.1.0 二进制建 format-4 索引并写入 growing。原地升级后文件编号不变，122 行评分完全相同。另通过 1.0.0、1.1.0 两条 SQL 升级入口、符号检查、启用共享后的 dump/restore，以及 RESET 后回退至原 1.2.0 库再升级。
- 在本地容器中分别对 Linux aarch64、x86_64 运行 PG 15.20、16.16、17.12、18.7、19.0。十个组合各通过 xtask 构建与 Clippy、19 个 SQL 文件、并发 VACUUM、符号及两个升级入口。18 和 19 另跑恢复与主备。两个架构的 PostgreSQL、扩展与并发 VACUUM 程序均原生运行。arm64 容器内的 SQLLogicTest 客户端使用 Docker 的二进制转译。首轮发现 PG 19 锁模式 FFI 参数类型差异，修复后重跑全部组合。
- Rust 1.100.0 下通过 rustfmt、纯 Rust 工作区测试和 Clippy、xtask 构建和 Clippy。Taplo 已检查受版本控制的 TOML。配套中英文参考文档位于站点本地提交 `90a2dc6`，Hugo 生成 921 个 HTML 文件，内部目标和片段均无缺失。

两机使用同一份压缩语料。中英文技术文档段落经过抽样拼接，并加入可复现的稀有词。主基准 20,000 行，追加测试另加 2,000 行。两平台均设置 256 MiB shared_buffers，主基准串行构建，m3 的集群位于 tmpfs。结果反映热缓存下的构造负载。

性能基准按基线、修改版、修改版、基线的顺序各开新集群。每集群建索引三次。普通查询预热一次后取五次执行中位数，表内的标量全表求和与无限制排序取三次。查询结果再取各集群中位数的中位数。建索引数据取六次构建的中位数，维护数据取各观察值的中位数。计数四舍五入。构建与维护使用客户端计时，查询耗时和块访问取自 EXPLAIN ANALYZE。WAL 条数按索引筛选 Generic 记录，字节数为这项操作起止 LSN 的全体 WAL 差值。

配套证据包中的 `macos-arm64/` 和 `m3-x86_64/` 各含四份 `paired-*.jsonl`、子计划和 worker 测量、构建与验收日志。独立原型数据位于 `prototypes/`，双架构矩阵日志位于 `checks/`，输入和复跑脚本位于 `bench/`。
